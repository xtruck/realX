# B1 - Backend audit: server.py, ws.py, log.py

Branch `audit-backend-b1-server` (from `photoreal-integration`, f8f989e). Read-only audit: no application code or test changed.
Date 2026-10-21. Platform: Windows 11, CPython 3.12.

Note: `docs/audit/AUDIT-2026-10-21.md` (the prior pass, finding A7) does not exist in this branch, so it could not be read. Auth, Host, Origin, CSP and path traversal were treated as out of scope as instructed.

## Summary

The three files are, on the whole, carefully written: the WebSocket parser rejects unmasked, oversized, reserved-bit and malformed frames correctly, publisher and viewer loops are "latest value wins" (no unbounded per-client queue), all JSON routes reject NaN/inf/bool/wrong-type/huge-number input with a clean 400, shutdown is fast and clean (0.01 s, all threads gone, same port reusable), and no secret reaches the log.
The real problems are in the HTTP layer around them. One High: an MJPEG client thread never notices its client has gone while no JPEG is being produced (body/character/photoface mode), so the slot is held until a video mode resumes, and with the 16-connection cap this can lock the whole server out (503 for everything, API included). Four Medium: slow-trickle clients can occupy all 16 slots before authentication; `do_GET` has no exception handling (a raising route gives an empty reply and a stdlib traceback on stderr that bypasses `realx.log`, and every client reset prints a traceback); Windows lets a second server bind the same port silently (SO_REUSEADDR); and a JPEG is encoded on every frame on the engine thread even with no viewer (17.6 ms at 720p, 34 ms at 1080p measured here, against a 33 ms budget at 30 fps). The rest are Low/Info hardening and consistency items.

Counts: Critical 0, High 1, Medium 4, Low 12, Info 5 (22 total).

Repro harness: in-process `Server(Engine(mode="body"), port=0, token=...)` (body mode needs no model files), raw sockets from the same Python. Scripts were kept in the scratchpad, not committed.

## Verified OK

- Input validation of every JSON route: `/api/config` (NaN, inf, 1e999, bool, string, list/dict values for mode/source/background, blur type and range), `/api/dock`, `/api/emote` (list/dict/None name), `/api/facemesh/consent*` (invalid UTF-8, 3000-deep nesting caught as RecursionError, non-object, bad hours), `/api/voice` (semitones nan/inf/abc/1e999 all 400, code range check in `offline`). All return a clean 400/403 JSON; none raised 500.
- Body limits: negative / over-limit / chunked Content-Length rejected (code); `_drain` bounded to 64 KiB.
- WebSocket: masking enforced, size caps (1 KiB viewer, 6 KiB publisher), RSV bits, control frame size, UTF-8 check, partial frames and byte-at-a-time delivery, ping/pong, close handshake echo, publisher cap of 200 frames/s, 15 s idle drop (observed 15.1 s), single publisher (409 for a second), publisher claim released after oversize, invalid message, abrupt RST and idle drop.
- No unbounded per-client buffers: viewers/MJPEG hold only references to the newest JPEG/rig string; `_inbuf` is capped; `_ribbon` is a bounded deque; `_GZIP_CACHE` is keyed by a fixed asset set; `model_cache` has at most 4 entries; `Dedup` is size-capped (but see B1-06).
- Shutdown: `Server.stop()` with an open MJPEG client and an open viewer socket took 0.01 s and left only the main thread; second `stop()` and `stop()` without `start()` are safe; restarting on the same port works.
- Lock discipline in `Engine`: one `Lock` shared by the `Condition`, no nested acquisition (`dock_state` takes no lock; `set_dock` calls it while holding it, which is fine); `wait_update` cannot miss an update because it compares the revision.
- Latest-wins backpressure: a stalled viewer or MJPEG client blocks only its own thread; `sendall` is bounded by the 15 s socket timeout.
- `_accepts_gzip` q-value handling (`gzip;q=0`, `*;q=0, gzip`, `q=nan`); gzip body and `Content-Length` consistent.
- Time handling: durations use `monotonic`/`perf_counter` (body age, emote age, hardware cache, rate limiting, drain); wall clock only for consent expiry, where an absolute epoch is the point.
- Secrets in logs: no log call includes the token, headers, cookies, body or query; paths are `clip`ped; the error JSON for 500 is generic and the details go to the log only (POST).
- CRLF: MJPEG framing uses explicit `\r\n`; no text-mode file I/O in these files (avatar read in `rb`).
- Engine thread cannot die from a normal fault: both `SourceError/StopIteration` and generic exceptions back off and rebuild (the only escape is B1-06).

## Not verified

- Real camera behaviour (open/close, blocking read at stop, B1-20), real pipeline cost per stage and the 3.1 fps seen in `original` mode on this machine.
- Browser behaviour (reconnect logic, how the page reacts to a 503 or an empty reply); no Chrome was run.
- Memory effect of large declared Content-Length (B1-22) and `/api/voice`/`/api/background` with real payloads.
- Whether the Nagle/delayed-ACK effect (B1-16) is real; measurements were noisy.
- Half-open TCP peers (needs a network fault, not simulated) for viewers and the publisher.
- Port hijack by a second process binding a more specific address (B1-04 only demonstrated for two realX servers).
- The `realx serve` CLI, KeyboardInterrupt path and logging configuration (in cli.py, outside scope).
- Model download behaviour (`ensure_model`) and consent/crypto internals.
- Existing test files were not run (the repro scripts exercised the same paths directly).
